# 从真实痛点到产品：Agent 会话管理器创作案例

## 这个项目是做什么的

Agent 会话管理器是一个本地只读的 AI 会话管理工具。它可以读取用户电脑里的 Codex 和 Claude Code 会话记录，把原本分散在本地数据库、JSONL 文件、日志和归档目录里的历史对话，整理成一个清晰的可视化界面。

它解决的核心问题是：

> 当一个人同时使用 Codex 桌面端、Codex CLI、`codex exec`、Claude Code、Obsidian 插件、Lark / Coze Bridge 等不同入口时，会话记录会分散在不同地方，事后很难找回、筛选、复盘和继续。

这个工具把这些分散的会话统一呈现出来，让用户可以：

- 快速搜索历史会话。
- 判断会话来自哪个入口和场景。
- 查看当时完整的对话过程。
- 展开每一轮回复里的工具调用和处理过程。
- 一键复制恢复命令，继续之前的 session。
- 按时间、来源、场景、重要性、模型服务商和归档状态筛选。
- 查看 Token 消耗、Skill 使用频率和活动热力图。
- 区分真正重要的项目会话和普通测试会话。

所以它不是一个展示型 Demo，而是一个直接进入真实工作流的本地工具。它的价值不在于“做了一个页面”，而在于把用户过去和 AI 协作产生的上下文重新组织起来，让历史会话可以被找回、被理解、被复用。

这个案例适合放进课程里讲，是因为它完整展示了一个 AI 产品从 0 到 1 的过程：先有真实痛点，再通过对话把问题说清楚，然后让 Codex 读取真实本地数据、设计界面、实现功能、持续修改，最后沉淀成 GitHub 上可维护的项目。

这份文档用于课程讲解，核心不是介绍一个工具，而是拆解一次完整的 AI 产品创作过程：用户从自己的真实痛点出发，通过持续和 Codex 沟通，让 AI 逐步理解需求、读取本地数据、设计产品、实现功能、修正体验，最终做成一个可以长期使用的本地会话管理器。

这个案例适合用来讲“Codex 做内容和做产品的逻辑”：不是先写一个完美需求文档，再让 AI 一次性生成结果；而是在真实使用场景里，一边发现问题，一边把问题说清楚，一边让 AI 去验证、实现和迭代。

## 一、项目背景：解决了什么痛点问题

最开始的问题很具体：电脑里同时安装了 Codex 桌面版和 Codex CLI，也会在不同入口里使用第三方 API、ChatGPT 官方账号、终端、Obsidian 插件、Bridge 环境等。不同入口都会产生会话记录，但这些记录并不总是在同一个客户端里可见。

典型痛点包括：

- 在 Codex 桌面端用 ChatGPT 官方账号登录时，看不到使用 API 时产生的 session。
- 在 CLI 或终端里使用 Codex 时，也会产生 session，但桌面客户端里不一定能找到。
- 同一个需求可能在多个环境里继续推进，事后很难知道这段对话到底来自哪里。
- 有些 session 很重要，比如完整做了一个产品；有些只是测试连通性，比如只说了一句“你好”，没有保存价值。
- 本地 session 数据分散在 SQLite、JSONL、日志和归档目录里，普通用户很难直接阅读。

所以这个产品最早的目标非常清晰：

> 做一个可视化的 session 管理器，知道每个 session 来自哪个客户端、ID 是多少、能不能复制恢复命令，并且可以像 Codex 桌面端一样查看当时的对话过程。

这个痛点有两个关键特征。

第一，它不是虚构出来的创业点子，而是使用者自己每天真实遇到的问题。真实痛点天然会带来清晰的判断标准：这个工具有没有用，不看功能多不多，而看它能不能帮我快速找到过去的会话、恢复上下文、判断重要程度。

第二，它不是一个纯内容问题，而是一个“数据理解 + 产品设计 + 前端体验 + 本地工具”的综合问题。AI 不能只靠文字想象，必须读取真实本地数据，理解 Codex session 的存储结构，再把这些数据转成用户能看懂的界面。

## 二、沟通过程：中间是怎么去聊的

整个沟通过程并不是一次性完成，而是分阶段推进。每一轮对话都围绕一个具体问题展开，AI 根据最新反馈继续调整产品。

### 1. 先问机制，而不是直接做界面

最开始没有直接让 AI 写代码，而是先问：

> Codex 的 session 之间的管理机制是怎样的？

这一步很重要。用户并不是只想要一个漂亮界面，而是想搞清楚底层逻辑：为什么桌面端、CLI、API、账号登录产生的记录不互通？这些 session 存在哪里？ID 怎么查？恢复命令是什么？

这相当于先让 AI 建立“问题模型”。只有理解了 session 的来源、存储和恢复机制，后面做出来的管理器才不是表面工具。

### 2. 再明确产品形态：要可视化、清晰、像 Codex 桌面端

明确机制之后，用户提出第二层需求：

> 帮我做一个可视化的 session 管理器，界面跟 Codex 桌面版类似，清晰、明了、简洁，可以复刻 OpenAI 官方设计风格。

这里的表达非常有效，因为它同时给了 AI 三个边界：

- 产品类型：可视化 session 管理器。
- 审美方向：类似 Codex 桌面版。
- 体验要求：清晰、明了、简洁。

这比只说“做得好看一点”更容易落地。AI 可以围绕已有的 Codex 桌面体验去做模仿，包括左侧会话列表、中间对话记录、右侧技术索引、卡片信息和简洁配色。

### 3. 用截图持续校准，而不是抽象批评

后续很多迭代都来自截图反馈。比如：

- 来源下拉菜单出现乱码，需要改得清晰。
- Conversation 区域里反复出现“codex”，不符合桌面端体验。
- “已处理”过程被全部汇总到一起，不能看出每一轮回复中 AI 是怎么处理的。
- Markdown 表格和公式渲染不好，内容不清晰。
- 右侧 Technical Index 需要折叠，避免遮挡主要对话。
- 重要性判断面板放错位置，导致界面混乱。
- 最上方摘要卡片重复显示第一条聊天记录，应该去掉。
- 热力图缺少月份标注和当天 Token 提示，不够直观。

这些反馈有一个共同点：用户不是泛泛地说“还是不好”，而是指出具体界面位置、具体问题、具体希望怎么改。AI 也因此能快速定位到代码里的组件和样式，持续迭代。

### 4. 需求逐步从“能用”走向“适合长期使用”

产品一开始只要解决“找到 session 和复制 resume 命令”。但随着可用性提高，需求逐渐变得更细：

- 增加重要性判断，区分重要会话和测试会话。
- 增加按时间、来源、服务商、重要性的筛选。
- 把来源拆成两层：入口来源和场景标签。
- 增加用量统计，显示 Token 消耗和 Skill 使用频率。
- 支持 GitHub 仓库、README 和公开发布。
- 从 Codex 会话管理扩展到 Claude Code 会话管理。

这就是 AI 产品常见的真实演进方式：不是一开始就规划所有功能，而是在一个核心痛点被解决后，再围绕真实使用继续生长。

## 三、AI 实践：AI 是怎么去做的

这个案例里，AI 不是只负责“写代码”，而是承担了多个角色：需求分析、数据侦察、产品设计、前端实现、后端接口、测试验证、Git 管理和文档整理。

### 1. 先读取真实本地数据，而不是凭空猜

AI 首先检查本机 Codex 数据结构，包括：

```text
~/.codex/state_5.sqlite
~/.codex/logs_2.sqlite
~/.codex/sessions/**/*.jsonl
~/.codex/archived_sessions/*.jsonl
```

后续扩展 Claude Code 后，又读取：

```text
~/.claude/projects/**/*.jsonl
```

Claude Code 的统计直接扫描当前可索引的会话 JSONL，不依赖可能滞后的 `stats-cache.json`。这样会话总数、每日 Token、单会话峰值和模型使用情况都能与当前会话列表保持一致。

这一步解决了一个关键问题：session 管理器不是编一个列表，而是要从真实数据源里提取会话 ID、标题、更新时间、来源、模型、Token、rollout 文件、日志数量、归档状态等信息。

AI 的实践逻辑是：

1. 先找数据源。
2. 再分析字段含义。
3. 再设计 API 返回结构。
4. 最后把数据渲染成用户界面。

这是做工具类产品非常重要的方法：不要先做 UI，再想数据；而是先确认数据能不能稳定拿到。

### 2. 用本地 Web App 承载产品

产品采用轻量本地 Web App 的形式：

```text
server.js       本地 Node 服务和 API
public/app.js   前端交互逻辑
public/styles.css  界面样式
public/index.html  页面结构
```

这个选择很务实：

- 不需要复杂前端框架。
- 不需要数据库迁移。
- 不上传用户隐私数据。
- 本地启动后浏览器访问即可使用。
- 方便快速迭代 UI。

服务端负责读取 SQLite 和 JSONL，前端负责筛选、展示、折叠、复制命令和统计弹窗。

### 3. 把“来源”从粗糙字段升级成产品可用标签

最早 Codex 数据里的 `source` 可能只是 `vscode`、`cli`、`exec`、`unknown`，甚至有些是 JSON 字符串。直接展示给用户会非常混乱。

AI 后来把来源拆成两层：

第一层是入口来源：

- Codex 客户端
- Terminal / Codex CLI
- Terminal / codex exec
- Obsidian / Claudian
- Bridge / Lark
- Bridge / Coze
- 子代理
- 未识别入口

第二层是场景标签：

- 飞书 / Lark
- Obsidian 笔记
- Coze / Bridge
- Skill 工作流
- SDK 接入
- 终端项目
- Codex 项目
- 普通会话

这里体现了一个产品设计思路：底层字段不等于用户语言。AI 要把机器字段翻译成用户能理解、能筛选、能做决策的标签。

### 4. 按真实使用路径设计界面

界面不是为了展示所有信息，而是为了支持用户最常见的操作：

1. 在左侧快速搜索会话。
2. 按入口来源、场景标签、时间、重要性过滤。
3. 点击会话后查看中间的对话记录。
4. 必要时展开每轮回复里的处理过程。
5. 复制恢复命令继续会话。
6. 需要排查时再打开右侧技术索引。
7. 想复盘使用情况时打开用量统计。

因此产品把信息分成了几个层级：

- 高频信息：会话标题、更新时间、来源、场景、重要性。
- 操作信息：恢复命令、复制按钮。
- 主要内容：对话记录。
- 辅助信息：技术索引、日志、Token、文件路径。
- 统计信息：Token 热力图、Skill 使用频率。

这也符合课程里可以强调的一点：好产品不是信息越多越好，而是把信息放在合适的位置。

### 5. 让对话记录尽量还原 Codex 桌面端

用户反复强调：中间 Conversation 区域要像 Codex 桌面端，不能只是把 JSONL 事件粗暴打印出来。

AI 因此做了几个处理：

- 按用户提问和 AI 回复组织成一轮一轮的对话。
- 每轮回复里的工具调用、Skill、执行过程做成可展开的“处理过程”。
- 最终回复按 Markdown 渲染，支持表格、代码块、引用、公式。
- 避免反复显示无意义的 `codex`、`user event assistant` 等技术角色名。
- 技术事件不抢主视图，需要时再展开。

这一步很关键，因为 session 管理器的核心不是“读取文件”，而是“让人重新看懂当时发生了什么”。

### 6. 增加本地启发式重要性判断

用户提出一个很真实的需求：

> 当前这个 session 是重要呢，还是不重要？比如现在这个产品开发会话很重要，但只是测试“你好”的会话不重要。

AI 没有引入复杂模型，而是先做了本地启发式判断，根据会话长度、任务关键词、Token 消耗、多轮对话、是否有完整目标等维度给出分数。

这是一种很适合工具产品的做法：先用足够透明、可解释的规则解决 80% 的需求，而不是一开始就做复杂 AI 分类。

### 7. 加入用量统计，把工具变成复盘系统

后期增加了“用量统计”弹窗，统计内容包括：

- 累计 Token 数
- 单会话峰值 Token
- 最长任务时长
- 会话总数
- Skill 使用频率
- Token 活动热力图

热力图后来又继续优化：

- 按周分列、按天分行。
- 增加月份标注。
- 鼠标悬停显示当天 Token 消耗。
- 低到高用不同蓝色深浅表示。

这让产品从“查找会话”进一步变成“复盘自己如何使用 AI 的系统”。

### 8. 用 GitHub 管理项目，让一次对话产出变成正式资产

产品完成后，AI 继续做了工程化处理：

- 初始化 Git 项目。
- 写 README。
- 新建 GitHub 仓库。
- 推送代码。
- 设置公开仓库。
- 后续每次重要功能更新都提交并推送。

Git 历史也记录了产品演进：

```text
cac0658 Initial Codex session manager
56cc8f0 Add entry source and scene filters
3c5c6e2 Improve token activity heatmap
2374ded Rename to Agent 会话管理器 and add Claude Code session management
0d9dda0 Add manual archive toggle for sessions
```

这对于课程非常有价值，因为它证明：AI 不是只能生成一次性内容，也可以帮助把一个想法推进成可维护的项目。

## 四、最终成果：最终是怎么做成一个产品的

最终产品从“Codex session 管理器”升级成了“Agent 会话管理器”。

它现在支持两套模式：

- Codex 会话管理
- Claude Code 会话管理

核心能力包括：

- 本地只读读取会话数据。
- 会话列表浏览。
- 按入口来源筛选。
- 按场景标签筛选。
- 按模型服务商筛选。
- 按时间范围筛选。
- 按重要性筛选。
- 按归档状态筛选。
- 一键复制恢复命令。
- 按轮次还原对话记录。
- 每轮处理过程可折叠展开。
- Markdown、表格、代码、公式渲染。
- 技术索引可折叠。
- Token 用量统计。
- Skill 使用频率统计。
- Token 活动热力图。
- 手动归档标记。
- GitHub 公开仓库和 README。

从用户角度看，它解决的是：

> 我过去和 AI 的重要对话，都能被找回、看懂、筛选、恢复和复盘。

从课程角度看，它展示的是：

> AI 产品不是凭空生成的，而是从一个真实痛点开始，通过持续对话、真实数据验证、界面迭代和工程化交付逐步长出来的。

## 五、这个案例适合讲给学员的核心逻辑

这门课如果用这个案例，可以重点讲四句话。

### 1. 好项目往往来自自己的真实痛点

这个项目不是为了练手而练手，而是因为使用者真的找不到自己的 session，真的需要恢复命令，真的需要知道每个会话来自哪里。

真实痛点会让需求更具体，也会让验收标准更明确。

### 2. 跟 AI 沟通时，要从“我要什么”逐步推进到“哪里不对”

一开始说目标：

> 我要做一个 session 管理器。

中间说风格：

> 要像 Codex 桌面端一样清晰、简洁。

后面说具体问题：

> 来源下拉有乱码。

> Conversation 内容被遮挡。

> 已处理不能全部汇总，要放回每一轮问答里。

> 表格和公式要正确渲染。

> 热力图要有月份标注和当天 Token 提示。

这种沟通方式非常适合 AI 编程：先给方向，再用具体反馈不断收敛。

### 3. AI 做产品不是一次生成，而是持续迭代

这个项目经历了多个阶段：

1. 理解 session 机制。
2. 做出最小可用界面。
3. 优化来源显示和恢复命令。
4. 还原对话过程。
5. 增加重要性判断。
6. 增加筛选器。
7. 增加统计弹窗。
8. 优化热力图。
9. 接入 Claude Code。
10. GitHub 项目化。

这说明 AI 最强的地方不是“一次性猜中所有需求”，而是可以在用户持续反馈下快速修改、验证和推进。

### 4. 最终产品要回到真实工作流

这个工具不是展示型 demo，而是放在本地长期使用：

```bash
npm start
```

打开：

```text
http://127.0.0.1:8787/
```

它读取的是本机真实会话数据，复制的是真实恢复命令，显示的是真实 Token 和 Skill 使用记录。这就是 AI 做工具最有价值的地方：不是生成一个看起来像产品的页面，而是让产品进入自己的真实工作流。

## 六、可直接用于课堂的讲解结构

如果要在课上讲，可以按下面这个顺序：

1. 先展示痛点：为什么 Codex / CLI / API / Obsidian / Bridge 的会话不好管理。
2. 展示最初的问题：我不是先让 AI 写代码，而是先问 session 管理机制。
3. 展示第一版产品：本地读取 Codex session，能看到列表和恢复命令。
4. 展示迭代过程：用截图指出界面问题，让 AI 持续改。
5. 展示关键产品能力：Conversation、处理过程折叠、重要性判断、来源筛选、场景标签、统计热力图。
6. 展示工程化结果：README、GitHub、公开仓库、后续提交历史。
7. 总结方法论：真实痛点、具体反馈、数据验证、快速迭代、进入工作流。

## 七、这个案例背后的方法论

可以把这个案例总结成一个简单公式：

```text
真实痛点
→ 让 AI 理解机制
→ 用本地真实数据验证
→ 做最小可用产品
→ 按截图和体验持续反馈
→ 把功能放回真实工作流
→ GitHub 项目化沉淀
```

这也是学员最应该学会的地方。

很多人使用 AI 时，只停留在“帮我写一段文案”“帮我生成一段代码”。但这个案例展示的是更进一步的能力：把 AI 当成一个可以持续协作的产品工程伙伴，让它围绕自己的真实问题，一步一步做出一个真正能用的工具。
